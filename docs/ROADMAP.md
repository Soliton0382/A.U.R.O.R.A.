Already sealed: the anonymous chat (sys_anon), the backup (AES-256-GCM, its key outside it). Not a sink: the WebUI's
storage (preferences only), uvicorn (no access log), the deductions and the synapses (knowledge only — but they can
quote a chat's attached document while C453 lasts).

**Who it protects from.** Aurora must read a chat to answer, to consolidate at night, to dream: while she works
unattended her key is on this machine, and whoever is root can take it. What the plan gives: no plaintext on disk, in
the logs, in the backups or in another user's reach; the admin's account (in the services' group) and Aurora's own
pages never show another user's chat; a stolen disk or NAS copy holds ciphertext. Against root itself only a key
bound to the user's password helps (phase 7), and then the night's work for that user waits for their login.

**Phases**
1. **C453 first:** a chat's attached document goes to the user's own memory (an «attachment» domain, encrypted with
   the rest), never the shared knowledge; none written in the anonymous chat. Today's attached documents
   (origin «chat») moved to their user — the trace names the user of a run for 30 days; older ones to the admin.
2. **Keys:** one random 256-bit key per user in their state folder (0600, the services' account; hidden from the
   cages as keys/ is today); copied by the encrypted backup; a user's purge destroys it.
3. **The memory shards:** AES-256-GCM on text, title and extra of every conversation and reflection soliton (the sid
   as associated data); dates, kind, consolidated state stay plain for the queries. The readers decrypt
   (sol_reader, the REM, the diary through Aurora instead of the shard file); a text search becomes a scan in Python.
   The memory's lexical index keeps hashed words (a keyed hash per user), its vectors encrypted on disk and opened in
   memory. The migration of today's memory at an update, a copy first, rows of both kinds read meanwhile.
4. **The logs:** the trace keeps run ids, sids, lengths and times, never a chat's text (question, translation,
   draft, reasoning, answer, an agent's thoughts and arguments, search queries); api.log the same; the shared
   forge requests and autonomy ledger point to the run instead of quoting it.
5. **The user's status files:** shadow.db, review, study, mood and anger, approvals, plugin_shadow, the projects'
   talk, push history, line events, mask_learned, uploads, TTS cache, dream paintings — sealed with the user's key
   (the sys_anon format), or not kept where they are only a cache.
6. **Out of the machine:** the queries to the paper archives masked like the web search; the push body optionally
   just «Aurora replied»; a thought or dream that names a user never drawn for a post.
7. **Optional, per user:** the key bound to their password (unlocked at login, kept in memory for a while; written
   meanwhile with a public key) — not even root reads it while they are away; their night's work waits.

Each phase with its tests and a run of the throw-away user's search; the migration tried on the Ubuntu VM first.

### 🎧 DJ plugin — proposal (owner, 2026-10-04) — first version built 2026-10-05

"Not professional, a few ready presets": the owner's own tracks (uploaded or in a music folder) become a mix.
- **Presets, ready to go:** *smooth* (beat-aware crossfades, same loudness), *party* (tempo matched to one BPM, short

  chat ("fammi un mix party con questi tre brani"); the result in Files and playable in the chat.
- **Limits said plainly:** only music the owner has the right to use; a mix of others' songs stays private (no
  automatic social post, the AI Act mark on anything published); generating new music from nothing is not in this
  first version (the open models' licences to be checked first).
- **Measures before "done":** BPM detection against tracks of known tempo; a mix's beat alignment (offset in ms);
